# RYNJI 2.0 — питание: функциональная спецификация (фаза A)

Ориентир по функциям — уровень FatSecret. Оформление, тексты и иллюстрации — свои: экраны, графика и исходники FatSecret, Hevy и Fitbod не копируются.

## 1. Главный сценарий

```
Питание → день (недельная лента) → съедено / цель / осталось → Б/Ж/У
       → «+» у Завтрака / Обеда / Ужина / Перекуса
       → один поток добавления: Недавние · Избранное · Мои · поиск · штрихкод · фото*
       → порция (г, мл, шт, порция) → [в корзину | добавить]
       → «Добавить в обед» → дневник, тост «Добавлено в обед · Отменить»
```
\* Фото — только при работающем сервисе распознавания (§8).

### Критерии приёмки (измеряются e2e-сценариями)

| Критерий | Как проверяем |
|---|---|
| Повторный продукт — ≤ 3 ключевых действия | «+» у приёма → продукт в «Недавних» → «Добавить» (граммовка прошлого раза) = 3 тапа |
| Поиск не блокирует ввод | ввод доступен во время сетевого запроса; локальные результаты видны сразу, сетевые — добавляются ниже |
| Изменение граммов мгновенно пересчитывает КБЖУ | пересчёт при каждом изменении поля, без кнопки «Пересчитать» |
| Любое действие обратимо | удаление и копирование → тост с «Отменить»; изменение порции → можно вернуть прежнюю |
| Сохранение не стирает историю | записи хранят снимок КБЖУ; изменение продукта или рецепта не меняет прошлые записи (unit-тест) |
| Офлайн | без сети работают дневник, недавние, избранное, мои продукты, блюда, рецепты, базовые продукты |

## 3. Модель данных — изменения

Ключи хранилища (`form.nutrition`) не меняются. Версия persist растёт с 1 до 2, миграция в `merge`/`migrate` с unit-тестами на фикстурах прошлых версий.

```ts
/** Единица порции продукта. Масса всегда хранится в граммах (жидкости — через плотность, по умолчанию 1 г/мл) */
interface FoodUnit {
  id: 'g' | 'ml' | 'piece' | 'serving' | 'package';
  label: string;          // «шт», «порция 180 г», «пачка»
  grams: number;          // сколько граммов в 1 единице
}

interface FoodProduct {             // расширение текущего типа
  /* …существующие поля без изменений… */
  units?: FoodUnit[];               // v2: из serving при миграции → [{ id: 'serving', … }]
  densityGPerMl?: number;           // для мл
  verification: 'verified' | 'database' | 'label' | 'estimate';
  //            проверено     из базы      с этикетки  оценка (фото)
  attribution?: string;             // «Open Food Facts (ODbL)», «Powered by FatSecret»
}

interface FoodEntry {               // расширение
  /* …id, date, productId, name, grams, macros (снимок), meal, createdAt… */
  unit?: { id: FoodUnit['id']; qty: number; label: string }; // как ввёл человек
  recipeId?: string;
  estimate?: boolean;               // из фото: показывать «оценка»
}

interface Recipe {
  id: string;
  name: string;
  ingredients: { productId: string; name: string; grams: number; macros: Macros }[]; // снимок
  rawWeightG: number;               // сумма ингредиентов
  cookedWeightG?: number;           // вес готового блюда (уварка/ужарка)
  servings: number;                 // выход, порций
  per100: Macros;                   // на 100 г готового = сумма / cookedWeight
  createdAt: number; updatedAt: number;
}

interface DiaryDraft {              // корзина добавления, переживает закрытие приложения
  date: ISODate; meal: MealSlot;
  items: { product: FoodProduct; grams: number; unit?: FoodEntry['unit'] }[];
}
```

Правила:
- Изменение рецепта или продукта не трогает прошлые записи: в записи лежит снимок. Тест: изменить продукт → сумма прошлого дня не изменилась.
- Пересчёт без накопления ошибки округления: КБЖУ считаются от граммов и `per100` с полной точностью. Округление — только при показе. Сумма дня — сумма неокруглённых значений.
- Удаление: запись уходит в буфер на 8 секунд — успеешь нажать «Отменить» в тосте.

## 4. Поиск: `FoodProvider` и ранжирование

```ts
interface FoodProvider {
  id: 'local' | 'custom' | 'openfoodfacts' | 'usda' | 'fatsecret';
  label: string;                    // для группы результатов и атрибуции
  offline: boolean;                 // работает без сети
  search(q: NormalizedQuery, opts: { signal: AbortSignal; page?: number; locale: 'ru' }): Promise<FoodProduct[]>;
  lookupBarcode?(gtin: string[], opts: { signal: AbortSignal }): Promise<FoodProduct | { partial: { name: string; brand?: string } } | null>;
}

interface FoodSearchService {       // один вход для UI
  search(q: string, onPartial: (r: RankedResults) => void): AbortController;
  lookupBarcode(code: string, type?: string): Promise<BarcodeResult>;
}
```

- Провайдеры опрашиваются параллельно. Офлайн-провайдеры (`local`, `custom`, кэш) отвечают сразу, сетевые дописывают результаты, когда придут. Старый запрос отменяется через `AbortController`.
- Нормализация запроса: регистр, `ё → е`, лишние пробелы, единицы («5%» = «5 %»), транслитерация брендов («prostokvashino» → «простоквашино»).
- Синонимы: небольшой словарь в `data/foodSynonyms.ts` (курица ↔ куриное филе ↔ грудка, гречка ↔ гречневая крупа, йогурт ↔ йогурт питьевой…).
- Опечатки: расстояние Дамерау–Левенштейна ≤ 1 для слов до 6 букв и ≤ 2 для более длинных — только по локальным данным и кэшу. Сеть получает исходный запрос.
- Порядок результатов, по убыванию веса:
  1. избранное и мои продукты;
  2. уже ели (частота за 30 дней);
  3. точное совпадение названия или бренда;
  4. совпадение с начала слова;
  5. `verification` (проверено > база > этикетка);
  6. полнота данных (есть Б/Ж/У и клетчатка, есть порция);
  7. тип источника (базовые для «сырых» продуктов, брендовые при наличии бренда в запросе).
- Дубли (один штрихкод из разных баз) склеиваются, остаётся запись с лучшей полнотой.
- Пустой результат: «Ничего не нашлось по „…“. Проверь написание, попробуй бренд или добавь продукт с этикетки» + «Свой продукт».

## 5. FatSecret Platform API — через свой сервер

Отдельное архитектурное решение: **нужно ваше согласование** (договор и тариф FatSecret, хостинг сервера).

```
iPhone ──HTTPS──▶ RYNJI server (server/index.mjs) ──OAuth2 client credentials──▶ FatSecret
                  /v1/food/search?q=…&page=…
                  /v1/food/barcode/:gtin
```

- Ключ и секрет FatSecret — только в переменных окружения сервера. Никаких `EXPO_PUBLIC_*` для секретов: всё с этим префиксом попадает в сборку приложения и извлекается из неё. Это уже касается `EXPO_PUBLIC_COACH_KEY` (см. аудит §3).
- Сервер авторизует устройство: подписанный токен установки или Sign in with Apple. Сейчас «общий секрет» в приложении защитой не является.
- Атрибуция («Powered by FatSecret»), сроки хранения ответов, разрешённые поля и регионы — по условиям выбранного тарифа. До подписания условий провайдер выключен флагом, и UI работает без него.
- Кэш на сервере — в пределах, разрешённых лицензией. На устройстве сохраняется только добавленный в дневник продукт: это нужно для офлайна и снимка КБЖУ.

## 6. Карточка продукта и порция

- Название, бренд, фото (если есть у источника), источник и статус: «Проверено», «Из Open Food Facts — данные сообщества», «С этикетки — ваш продукт», «Оценка по фото».
- КБЖУ на 100 г / 100 мл и на выбранную порцию — две колонки.
- Количество и единица: г, мл, шт, порция, упаковка (из `units`). Варианты «как в прошлый раз 180 г», «100 г», «порция 250 г».
- Клавиатура: цифровая с десятичной запятой. Значение проверяется (1–5000 г).
- Приём пищи — переключатель вверху листа (по умолчанию тот, у которого нажали «+»).
- Действия: «Добавить в обед» (главное) и «В корзину» (второстепенное, если в корзине уже что-то есть или включён режим нескольких продуктов).

## 7. Штрихкод

Сканер (EAN-8/13, UPC-A/E) → свои продукты → кэш → FatSecret (если включён) → Open Food Facts → USDA → нашлось только название → «Дописать КБЖУ с этикетки» (название уже подставлено) → продукт сохраняется со штрихкодом и в следующий раз находится офлайн. Последний результат кэшируется. Сканер никогда не подставляет выдуманные КБЖУ.

## 8. Добавление по фото

Делается, только если сервер RYNJI развёрнут и модель распознавания разрешена. Сейчас сервер уже вызывает Claude для Coach и анализов, но для фото еды эндпоинта нет.

- `POST /v1/food/photo` → список «ингредиент — примерная масса — уверенность». Продукты сопоставляются с базой через `FoodSearchService`.
- Экран проверки: каждую строку можно изменить, удалить или заменить продукт. Пока человек не нажал «Добавить», ничего не сохраняется.
- Записи помечаются «оценка» (`estimate: true`) и показываются с этой меткой в дневнике.
- Сервер не настроен — кнопки «Фото» нет. Вместо неё в настройках объяснение, что нужно.

## 9. Рецепты и блюда

- **Мои блюда** — как сейчас: набор продуктов с граммами, добавляется одним действием.
- **Рецепт** (новое): ингредиенты, вес сырых, вес готового блюда, количество порций. КБЖУ на 100 г готового и на порцию. В дневник рецепт добавляется в граммах или порциях.
- Изменение рецепта не меняет прошлые записи (снимок). При изменении показываем: «Прошлые записи останутся как были».

## 10. Цели и энергия

- Цель — расчёт RYNJI: BMR (Mifflin) × бытовая активность + средние затраты на тренировки в день, плюс поправка цели. См. `features/nutrition/targets.ts`.
- **Три разных числа, которые не смешиваются:** съедено (дневник) · активная энергия (Apple Health, только показ) · цель (расчёт). Активная энергия из Health к цели не прибавляется: тренировки уже учтены в цели, сложение дало бы двойной счёт. Так и сейчас в коде — правило фиксируется тестом.
- Корректировка цели (адаптивная по тренду веса, коуч) — только предложение с «Применить», как сейчас.
- Объяснение «Почему такие КБЖУ» — по тапу на сводке.

## 11. Аналитика питания (контрольный экран №5)

- Периоды 7 / 30 / 90 дней: средние ккал, Б/Ж/У, клетчатка; % от цели; дни с записями.
- День считается учтённым, если в нём записано ≥ 2 приёмов или ≥ 800 ккал. Остальные дни в средние не входят, их число показывается.
- Связь с весом: не меньше 14 учтённых дней и 4 взвешиваний в периоде. Иначе — «Недостаточно данных: нужно ещё N дней с записями». Без процентов «точности».
- Тренд — скользящее среднее веса (уже есть в `features/progress/weightTrend`).

## 12. Ошибки, пустые состояния, офлайн

| Ситуация | Текст | Действие |
|---|---|---|
| Нет сети при поиске | «Нет сети — ищу в сохранённых и базовых продуктах» | список офлайн-результатов |
| База не ответила | «База продуктов не ответила вовремя» | «Повторить» |
| Ошибка базы | «База продуктов вернула ошибку» | «Повторить», «Свой продукт» |
| Нет результатов | см. §4 | «Свой продукт» |
| Штрихкод не найден | «Этого штрихкода нет в базах» | «Добавить с этикетки» |
| Пустой день | «Ничего не записано» | «Повторить вчерашний завтрак» (если был) |
| Нет цели | «Заполни профиль — RYNJI рассчитает КБЖУ» | «Открыть профиль» |

В вебе запросы к Open Food Facts блокирует CORS — это ограничение превью, не iPhone. Поиск на устройстве — **не проверено** в этой фазе.
